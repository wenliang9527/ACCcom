## 1. Core 串口与 RX 链路

- **[P1] 重连循环在 Close() 取消后仍可能把新打开的端口换上 `_port`**（SerialService.cs:538-543）。取消检查只在循环头（501-510）；`tempPort.Open()` 成功到 `_port = tempPort` 之间无 token 复查。时序：用户点关闭 → `Close()` 先 `_reconnectCts.Cancel()`（:176）再排空、关旧口；重连线程恰好已过取消检查、正在 open → 把新口赋给 `_port`，留下一个「用户已关闭却仍打开」的端口。修复：换口前复查 `token.IsCancellationRequested`，取消则关掉 tempPort 直接返回。
- **[P1] `Close()` 同步阻塞调用线程最长 2 秒**（SerialService.cs:180 `DrainPendingAsync(...).GetAwaiter().GetResult()`）。GUI 关闭路径 `ConnectionViewModel.ToggleOpenClose`（:221，UI 线程 await）→ `SerialConnectionManager.ToggleConnection`（:32）同步调 `serial.Close()`；洪流下 dispatch 队列 2 秒内排不空 → UI 冻结至 deadline。发送路径已有 SendAsync 先例（:292-299 同因）。修复：`ISerialService` 加 `CloseAsync`（默认包同步 Close，轻量实现零成本），SerialService 覆写真异步排空，ToggleConnection 关闭分支 await。
- **[P2] 并发写串口无串行化**：`TrySendPrepared`（SerialService.cs:362-400）无锁。同进程内两个真实并发源：GUI 触发器发送（TriggerService.Evaluate 在 drain 线程触发 SendCommand）与 UI 发送；MCP 侧 SDK 按调用并发派发工具（send 与 send_and_wait 可重叠）。`SerialPort.Write` 无线程安全保证，交错写 = 线上帧损坏。修复：单写锁（lock 或 SemaphoreSlim）包住 TrySendPrepared。
- **[P2] 桥/虚拟端 LogEntry 不带 ByteCount**（NetworkBridgeService.cs:154-161 TX、:262-269 RX；VirtualSerialService.cs:76-83/100-107）：消费端 `ResolvedByteCount()` 回退逐字符重扫 hex（DataFlowViewModel.cs:606），桥 RX 每包白扫一次——SerialService RX 已带（SerialService.cs:460）。修复：三处生产端补 ByteCount。
- **[P3] 注释失真**：DispatchRx「receive thread is the only writer in practice」（SerialService.cs:225-226）已不准确——重连成功路径（:545）也 DispatchRx，双写者下淘汰计数可能偶发多计。仅注释/计数精度问题。
- **已确认无问题**：DataReceived 线程只做读字节+建条目（ArrayPool 租还，:443-467）；DropOldest 深度先行读的淘汰计数；drain 循环每订阅者 try/catch（:201-211）；Close 排空语义（排空先于关口，:177-182）；DataBufferService 所有查询返回新 List（r163 彻底）；MultiPortService 锁纪律（双检注册、锁外关闭、ObjectDisposedException 兜底）；NetworkBridge 断连清理（Interlocked 交换清理 + HandleDisconnect）；ParityReplace/UTF8 编码/open 重试。

## 2. 协议解析引擎

- **[待确认·不改] C# Script 死循环防线只护调用方不护线程池**：`ExecuteAsync` 以 5s `WaitAsync` 超时（ParserEngine.cs:159），但 Roslyn 脚本无法安全中止——死循环脚本的线程**继续烧**，每次执行泄漏一个线程池线程，反复调用可线程池饥饿。属执行模型限制；可选缓解（独立进程/AppDomain 执行）为架构变更，列待确认。
- **已确认无问题**：异常隔离（编译/运行错误走 LastError+OnError，超时路径区分 cancelled）；ParserEngineCache（mtime 失效、竞态防重复引擎、容量逐出并 Dispose）；FrameBuffer（容量/帧长钳制、三策略、200ms 超时出帧、MaxInFlight=1 防解析器堆积）；hex 解析 Modbus 传输已全委托 HexHelper；`Regex.CacheSize=256` 静态提升有依据注释。

## 3. Modbus

- **[P2] 从站读寄存器异常码语义颠倒**（ModbusSlaveDevice.cs:111-112）：`count > 125`（数量=值错，应报 0x03 illegal data value）落在 0x02；`startAddr + count > regs.Length`（地址越界，应报 0x02 illegal data address）报 0x03。同类：HandleReadBits 地址越界报 0x03（:96-97）。参考 HandleReadBits 的数量分支（:92-93）是对的。修复：数量违规→0x03、地址越界→0x02，补契约测试。
- **已确认无问题**：CRC-16/Modbus 查表（CrcHelper.cs：0xA001 反射、init 0xFFFF、表由逐位算法构建、RTU 帧低字节在前 adu[^2]=crc low，有 oracle 测试）；MBAP `MaxBodyLength=254` 主/从共享（ModbusTcpTransport.cs:27-32、ModbusTcpSlaveTransport.cs:86）+ 部分读循环；RTU BuildAdu 精确尺寸（R111 教训注释在位）；pending 队列 RemoveHeadLocked 防误杀；寄存器边界 ushort→int 提升无回绕；TCP 从站 read==0 断开。

## 9. 已知遗留核实

### 9.1 发送通道路由下沉（R167 推迟项）——**仍在，证据如下**

桥接模式下统一路由模式为 `if (bridge.IsConnected) bridge.Send(...) else serial.Send(...)`，已有 3 处正确路由：
- `src/ACCcom/ViewModels/DataFlowViewModel.cs:951-960`（主发送栏，串口侧走 SendAsync 防 UI 冻结）
- `src/ACCcom/ViewModels/ShortcutViewModel.cs:242-246`（快捷发送）
- `src/ACCcom/ViewModels/LoopSendViewModel.cs:124`（循环发送）

**缺桥路由 3 处（直连 `_serial.Send`，桥接模式下数据不出网桥）：**
- `src/ACCcom/ViewModels/TriggerViewModel.cs:121` —— 触发器 SendCommand 动作；另注意此处 `isHex` 硬编码 `false`（TriggerRule 无 hex 标志，触发发送仅 ASCII）
- `src/ACCcom/ViewModels/MacroViewModel.cs:110` —— 宏步骤发送 `send: (cmd, isHex) => _serial.Send(cmd, isHex)`
- `src/ACCcom/ViewModels/ProtocolTestViewModel.cs:227` —— 协议测试步骤发送 SendCallback

计数口径：`NetworkBridgeService.Send` 自产 TX LogEntry 并经 `OnDataReceived` 回流（NetworkBridgeService.cs:154-163），与串口路径一致，统一发送通道不会造成漏计/双计。

**修复方向（阶段二）**：抽出共享发送通道（桥路由 + 串口回退封装为单一入口），6 处调用点全部委托，消除 3 处遗漏 + 3 处重复。
